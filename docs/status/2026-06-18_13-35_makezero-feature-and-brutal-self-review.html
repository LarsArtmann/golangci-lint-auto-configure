05What We Should Improve

Pervasive map[string]any weak typing (80 usages)

The config model uses map[string]any for LintersConfig.Settings, FormattersConfig.Settings, OutputConfig.Formats, and LintersSettingsV1. Every migration and merge does v.(map[string]any) type assertions. This violates the project's own principle: "Strong types over runtime checks — make impossible states unrepresentable."

Tradeoff The settings schema is golangci-lint's external contract — it evolves independently. Typed structs give compile safety but cost maintenance to keep in sync with upstream. This needs a deliberate decision (see #1 Question).

No coverage gate on DefaultLinterSettings

Nothing enforces that each linter in DefaultLinterSettings has a corresponding injection test. A table-driven test iterating over the map keys would prevent untested defaults from shipping.

07#1 Question I Cannot Answer

Invest in typed linter-settings structs, or keep map[string]any?

map[string]any is used 80 times across the config model. Every migration, merge, and clone does runtime type assertions. Typed structs would give compile safety and kill an entire class of panic risks. BUT: the settings schema is golangci-lint's external contract — it adds new linter settings every release. Typed structs mean a maintenance burden: every upstream release could require new struct fields.

Three viable approaches I cannot decide between:

  • A) Full typed structs — generate from golangci-lint's JSON schema (if one exists). Zero runtime assertions, but a code-gen step and sync risk.
  • B) Hybrid — keep map[string]any for the general config, but add typed accessors/getters for the linters we inject defaults for (the 11 in DefaultLinterSettings). Bounded scope, real safety where we touch it.
  • C) Status quo — accept any because the schema is external and dynamic. Add a typed wrapper only if assertion panics become a real problem.
My lean: Option B (hybrid) — it delivers safety exactly where we have the most assertions (migrations + default injection) without committing to tracking every upstream field. But this is your architecture call, not mine.
