## D) TOTALLY FUCKED UP (honest self-critique)

### D1. The funlen battle took 4 rounds

`runFixerMode` was 38 lines (>30 limit). First extraction (`prepareFixerRun`) brought it to 33. Golines reformatter re-expanded the compact calls back to 33. Then I re-compacted manually — golines re-expanded again (32). Finally I extracted `computeDryRunState` as a second helper to get under 30. This was 4 iterations on a single lint finding.

**Root cause:** I didn't account for the golines formatter's behavior. Golines wraps long calls across multiple lines, and each wrapped line counts toward funlen's line limit. The lesson: when a function is near the limit, the formatter will inflate it — extract more aggressively than you think you need to.

### D2. Two compile errors from carelessness

1. `mergeSecondaryRules` iterated `secondary.Rules` instead of `secondary` (the parameter is already `[]types.ExclusionRuleConfig`, not a struct with a `.Rules` field).
2. `prepareFixerRun` used `types.Priority` instead of `types.LinterPriority` (the actual return type of `ParsePriorityParam`).
3. `marshalConfig` used `errors.New` without importing `errors` (the `fmt` package wasn't imported and I initially used `fmt.Errorf`).

These are all "didn't read the existing code carefully" errors. Each cost a build+fix round-trip.

### D3. Did not update CHANGELOG for the formatter force-settings extension

The `injectDefaultFormatterSettings` now accepts a `force` parameter — this is a behavioral change (formatters can now be force-overwritten) but the CHANGELOG only mentions `--force-settings` in the context of linter settings.

### D4. No dedicated test for `mergeLintersExclusionRules` dedup

I fixed the merger path to deduplicate by RuleKey, but only tested the fixer path. The merger dedup is verified only indirectly through existing integration tests that may not exercise the dedup code path specifically.

### D5. The `linter_settings_generated.go` file got regenerated by BuildFlow

BuildFlow's pre-commit hook regenerated `pkg/constants/linter_settings_generated.go` (1143 lines changed). This is cosmetic (alignment), but it means the diff for this session is dominated by a generated file. It also got committed by the auto-commit daemon with a generic message (`8a287e1 feat(cli): update configure fixer and regenerate linter settings constants`).

## E) WHAT WE SHOULD IMPROVE (process & code quality)

### Process improvements

1. **Read the function signatures before extracting helpers.** The `types.Priority` vs `types.LinterPriority` error and the `secondary.Rules` error were both avoidable by simply reading the existing types.

2. **Account for the formatter when targeting funlen limits.** Golines will expand compact calls. Budget for 20-30% formatter inflation when estimating whether a function will pass funlen.

3. **Test both merge paths when fixing split-brain issues.** The fixer path (`updateExclusionRules`) and the merger path (`mergeLintersExclusionRules`) now both dedup by RuleKey, but only the fixer path has a dedicated unit test.

4. **Update CHANGELOG immediately when extending behavior.** The formatter force-settings extension is a behavioral change that should be in CHANGELOG.

### Code improvements

5. **`computeDryRunState` returns 3 values.** It's a code smell that this function bundles `isDryRun`, `originalCfg`, and `effectiveDryRun` into a single return. A small struct would be clearer, but it's minor.

6. **`mergeSecondaryRules` takes a pointer to a slice.** This is necessary (it appends), but the indirection makes it harder to reason about. The fixer's `mergeExclusionLinters` returns a new slice instead — inconsistent patterns.

7. **`errUnsupportedFormat` is a package-level sentinel.** It's correct (err113 compliance), but it's a new sentinel that should be registered with go-error-family if it's ever returned to a command boundary. Currently `marshalConfig` is only called from `SaveConfig` which wraps it, so it's fine.

### 2. Should the funlen limit be raised from 30 to 40?

The golines formatter (max-len 120) frequently expands compact single-line calls across 3-4 lines. This makes the 30-line funlen limit very tight for functions that call other functions with many parameters. The project already has `cmd_configure_fixer.go` needing two helper extractions to fit. Raising to 40 would reduce the need for artificial function splits. This is a policy decision.

### 3. Should `mergeSecondaryRules` and `buildRuleKeyIndex` be package-level functions or methods?

They're currently package-level functions in `pkg/config/merger_linters.go`, but they're only used by `mergeLintersExclusionRules` (a method on `*Merger`). They could be unexported methods or even inline lambdas. Making them package-level exposes them to other merger files, which could be either intentional (reuse) or accidental (coupling). This is a style preference.
