What the Integration Would Enable

A watch subcommand (or --watch flag on configure / analyze) that monitors .golangci.yml and/or Go source files, automatically re-running analysis or re-configuring when changes are detected. This has been listed as a low-priority backlog item in archived status docs since April 2026.

PRO

Arguments in favor of integration

01

Same Author, Same Ecosystem

Both are LarsArtmann projects with identical toolchains (Go 1.26, Nix flakes, golangci-lint, gogenfilter). Zero friction on contribution workflow and release cadence.

02

Shared Dependency: gogenfilter

Both projects already depend on gogenfilter/v3 for auto-generated code detection. Integration would reuse the same scanning logic for both file-watching filtering and config exclusion generation — no duplicated detection.

03

Rich Filtering Out of the Box

FilterExtensions(".go", ".yml"), FilterIgnoreDirs("vendor"), FilterGeneratedCode() — exactly what a linting watcher needs. No custom filter code required.

04

Debouncing Built-In

WithPerPathDebounce(300ms) prevents re-triggering analysis on rapid saves — a fully solved problem with global and per-path modes.

05

Composable Middleware Chain

MiddlewareRecovery() prevents a panic from killing the watch daemon. MiddlewareLogging() provides structured watch output. MiddlewareDeduplicate() avoids redundant runs.

06

API Stability Guarantees

Explicit API_STABILITY.md commits to semver with clear stable / evolving / deprecated tiers. Core types (New(), Watch(), Filter, Event) are marked Stable.

07

Minimal Real Dependency Footprint

Only fsnotify is a non-trivial direct dependency. go-gitignore is tiny. The rest (golang.org/x/time, gogenfilter) are already in the dependency graph or trivial.

08

Self-Healing + ENOSPC Handling

Production-grade: handles inotify budget exhaustion gracefully, retries failed paths. Important for large monorepos where max_user_watches limits are realistic.

09

Phantom Types for Path Safety

EventPath vs RootPath prevents mixing up watched roots with event paths at compile time — eliminates an entire class of bugs.

10

Well-Documented, Well-Tested Codebase

12,786 LOC total, 1,465-line test file, benchmark tests, fuzz tests, architecture docs, AGENTS.md. Passes go vet cleanly. 109 commits in the last month. Active, mature development.

CONTRA

Arguments against integration

01

Test Failure on This Machine

go test ./... FAILS with ENOSPC ("no space left on device"). Inotify limits are hit on the dev machine — a real operational concern for watching large projects. Integration would inherit this fragility.

02

Dependency Chain Expansion

Adds fsnotify, go-gitignore, golang.org/x/time to golangci-lint-auto-configure's dependency graph. Currently the project has zero filesystem-watching deps. Every dependency is maintenance burden (CVE surface, version skew, breakage).

03

Feature Scope Mismatch

go-filewatcher is a general-purpose library with circuit breakers, OTel tracing, Prometheus collectors, polling mode, content hashing — 90% of this is irrelevant for a simple "watch .golangci.yml and re-analyze" use case. You'd pay for complexity you don't use.

04

Alternative: Raw fsnotify (~20 LOC)

For watching a single config file (.golangci.yml), fsnotify directly is ~20 lines of code. The full go-filewatcher abstraction (filters, middleware, debouncers, phantom types) is over-engineered for this use case.

05

Alternative: External Tools (Zero-Dep)

Tools like air, watchexec, and entr already solve "run command on file change" as external processes. A just watch recipe calling watchexec is zero-dependency and more flexible.

06

No Existing Demand Signal

The --watch feature is consistently listed as Low priority / NOT STARTED across multiple status reports. No user requests, no GitHub issues, no roadmap commitment.

07

Runtime Model Change

A watch mode makes golangci-lint-auto-configure a long-running process instead of a one-shot CLI. This changes the operational model fundamentally: signal handling, graceful shutdown, resource cleanup, log rotation — all required.

08

Overhead from Unused Features

Circuit breaker, OTel, Prometheus, content hashing — these "evolving" APIs add import-time cost even if unused. The middleware system pulls in golang.org/x/time/rate unconditionally.

09

Version Coupling Risk

Since both are your projects, a breaking change in go-filewatcher v3 would force a coordinated release of golangci-lint-auto-configure. Manageable but real coordination overhead.

10

Evolving API Surface

Key features like WithSelfHeal, WithContentHashing, WithPolling, and all error middleware are in the Evolving stability tier — they can change behavior between minor versions.

Verdict

Do NOT integrate at this time

Factor Assessment
Library quality Excellent — well-designed, well-tested, documented, semver-committed
Fit for this use case Poor — watching 1–3 config files doesn't need 780 LOC of watcher abstraction
Demand signal None — consistently lowest priority across all planning docs
Risk / Reward Low — high dependency cost for a feature nobody's asking for

Recommended Path Forward

If --watch ever becomes a priority

Phase 1 — Lightweight Zero deps

Add a just watch recipe using watchexec or entr — zero Go dependencies, immediate value.

# justfile
watch:
watchexec -w .golangci.yml -e yaml -- just analyze
Phase 2 — If Needed 1 dep

Use raw fsnotify directly (~30 lines) for the single-file .golangci.yml watch case. No library needed. One dependency, full control, minimal abstraction.

Phase 3 — Whole Source Tree Watching go-filewatcher

THEN consider go-filewatcher. Its filtering, debouncing, and self-healing genuinely justify the dependency when you're watching thousands of .go files, not one YAML file. The library shines at scale — and the use case isn't there yet.

The library is excellent. The use case isn't there yet.

Revisit when --watch receives real demand.
