Architecture Deep-Dive

Split-Brain: Two Models, One Codebase

The data model has fractured along historical fault lines — parallel config hierarchies, three severity enums bridged by hand-written converters, a branded type system applied in some places and ignored in others. Every split is a place where a future change can land on the wrong copy and silently pass type-checking.

00Summary

A split-brain is when the same domain concept is represented by two or more divergent types, with no compile-time guarantee they stay in sync. This audit found seven split-brain clusters across the codebase. The worst is a complete mirrored configuration hierarchy in pkg/migration that duplicates pkg/types field-for-field under different names. The most dangerous is a triple severity/priority enum system where a Warning on one side becomes an Error on the other — a mapping that looks correct until a user asks why their warnings are failing CI.

None of these block compilation today. All of them tax every future change to the domain model: each new field, each new enum value, each new recommendation must be added in multiple places, and forgetting one produces a silent semantic gap rather than a build error.

Root cause Three independent origins: (1) the golangci-config-migrator merge brought its own type hierarchy and it was never unified; (2) the branded types (LinterName, ConfigPath) were introduced as a half-measure and never propagated to struct fields; (3) the go-finding integration introduced a third severity enum and the bridge was written ad hoc.

02Parallel Config Hierarchy

Critical · 11 mirrored types

Two complete config schemas, field-for-field duplicates under different names

pkg/types/types.go ↔ pkg/migration/config_types.go

The pkg/types package defines the canonical v2 config: Config, RunConfig, OutputConfig, LintersConfig, LintersExclusionsConfig, ExclusionRuleConfig, IssuesConfig, FormattersConfig, FormattersExclusionsConfig. The pkg/migration package defines a near-identical set under different names: Config, Run, Output, Linters, LintersExclusions, ExclusionRule, Issues, Formatters, FormattersExclusions, plus a legacy ExcludeRule and RunIssues.

The fields match. The yaml tags match. The intent matches. But because the type names differ, Go's type system cannot catch drift. If a field is added to types.LintersConfig and forgotten in migration.Linters, the migrator silently drops it — no compile error, no test failure, just data loss on the next migration.

types.Config ├── RunConfig ↔ migration.Run ├── OutputConfig ↔ migration.Output ├── LintersConfig ↔ migration.Linters │ └── LintersExclusionsConfig ↔ migration.LintersExclusions │ └── ExclusionRuleConfig ↔ migration.ExclusionRule ├── FormattersConfig ↔ migration.Formatters │ └── FormattersExclusionsConfig ↔ migration.FormattersExclusions └── IssuesConfig ↔ migration.Issues 11 types mirrored · 0 compile-time drift checks
Fix Two viable paths. (A) Migration embeds the canonical types and adds only the v1-only fields as a separate struct, so shared fields are literally the same type. (B) Migration defines a thin v1-read schema whose only job is yaml.Unmarshal, then converts to types.Config immediately — the v1 schema never escapes the migration package boundary. Path B is safer because v1 legitimately has fields v2 does not.

Before / After: Linters section

Before — Two types
After — One type, embedded
// pkg/types/types.go
type LintersConfig struct {
    Enable     []string
    Disable    []string
    Default    string
    Settings   map[string]any
    Exclusions LintersExclusionsConfig
}

// pkg/migration/config_types.go
type Linters struct {
    Settings   map[string]any
    Default    string
    Enable     []string
    Disable    []string
    Exclusions LintersExclusions
    EnableAll  bool   // v1-only
    Fast       bool   // v1-only
}
// pkg/migration/config_types.go
type Linters struct {
    types.LintersConfig    // embedded
    EnableAll bool `yaml:"enable-all"`
    Fast      bool `yaml:"fast"`
}

The migration Linters now is-a types.LintersConfig for all shared fields. Drift becomes impossible for those fields; v1-only fields remain explicit. The same pattern applies to Run, Output, and the exclusion types.

03Severity Babel

Critical · silent semantic drift

Three priority/severity enums bridged by hand-written converters

types.LinterPriority · types.HealthSeverity · finding.Severity

The codebase has three parallel enums that all encode "how bad is this":

  • types.LinterPriority — Critical, High, Medium, Optional (for linter recommendations)
  • types.HealthSeverity — Critical, Warning, Info (for config structural health)
  • finding.Severity — Critical, Error, Warning, Info (external go-finding package)

Two converter functions glue them together: PriorityToSeverity in pkg/finding/converter.go and SeverityFromHealthSeverity in pkg/finding/helpers.go. The second one contains a mapping that should make any reviewer pause:

Suspicious mapping HealthSeverityWarning → finding.SeverityError. A warning becomes an error. There is no comment explaining why. If this is intentional (treat warnings as errors in CI), it deserves a comment; if it is a bug, every health warning is escalating to a CI-failing error downstream.
LinterPriority → PriorityToSeverity → finding.Severity ← SeverityFromHealthSeverity ← HealthSeverity

Every new severity level on any side requires a case in two converters. Forget one and you get a silent default: return SeverityInfo — the lowest priority — which downgrades critical findings to informational.

Fix Adopt finding.Severity as the single severity vocabulary across the codebase. Delete HealthSeverity (its three values map cleanly). Rename LinterPriority to LinterRecommendationLevel so it stops colliding semantically with "severity" — it is a recommendation strength, not an issue severity, and conflating them is what created the conversion mess.

04LinterName Brand Gap

High · brand applied halfway

LinterName exists but config fields use []string

types.LinterName · LintersConfig.Enable []string · 8+ cast sites

The branded type type LinterName string exists specifically to "prevent typos in linter names" — yet the very struct that holds linter names uses raw []string: 

// What the config schema says
type LintersConfig struct {
    Enable  []string  `yaml:"enable"`
    Disable []string  `yaml:"disable"`
}
// What every consumer does
constants.DeprecatedLinters[
    types.LinterName(linter)]   // cast
constants.DefaultLinterSettings[
    types.LinterName(linterName)] // cast

The cast types.LinterName(linter) appears at least 8 times across pkg/linter/fixer_config.go, fixer_preflight.go, fixer_deprecated.go. Every cast is a place where a typo like "govit" would pass the brand check — because the brand is only applied after the value has already flowed through the system as an unbranded string.

The constants maps (LinterPriorities, LinterReasons, DeprecatedLinters) all correctly key on LinterName. But their map literals use string keys like "depguard", so the brand on the key side is purely decorative — Go converts the untyped string literal to LinterName automatically.

Fix Change LintersConfig.Enable and Disable to []LinterName. YAML/JSON unmarshaling works because LinterName has an underlying string type. The 8 cast sites collapse to zero. A typo in a linter name is now caught wherever it first enters the typed world, not wherever it happens to be looked up.

05ConfigPath Brand Ignored

High · brand defined, never used

ConfigAnalysis.ConfigPath is string, not ConfigPath

pkg/types/types.go:112-122 (definition) & :160 (usage)

The type ConfigPath is defined with IsValid() and String() methods — clearly intended for use. But the one struct that most obviously should use it doesn't: 

// Definition, with validation logic
type ConfigPath string

func (cp ConfigPath) IsValid() bool {
    return cp != ""
}
// Usage — the brand is discarded
type ConfigAnalysis struct {
    ConfigPath string  `json:"config_path"`
    // ...
}

Every downstream consumer (pkg/finding/converter.go, pkg/finding/detector.go, pkg/report/json_report_generator.go) takes configPath string as a parameter. The IsValid() method is never called. The brand provides zero protection today because nothing uses it. This is a brand that exists only to be ignored — worse than no brand at all, because it creates the illusion of type safety where none exists.

Either use it or delete it A branded type that nothing uses is dead code that misleads readers into thinking the path is validated. If IsValid() is never called, the validation does not happen.

06Name Collision: golangciLintOutput

Low · readability, not correctness

Same unexported name, two packages, two different shapes

pkg/linter/analyzer.go:46 & pkg/finding/golangci_lint.go:24

Two unrelated structs share the name golangciLintOutput:

Package Represents Fields
pkg/linter Linter listings from golangci-lint linters Enabled, Disabled []LinterInfo
pkg/finding Issue output from golangci-lint run --out json Issues []GolangciLintIssue

This is legal Go (unexported, different packages) but it is a trap for anyone grepping the codebase or reading import lists. The name suggests they are two versions of the same thing; they are not even the same kind of thing.

Fix Rename to reflect what each actually wraps: lintersListOutput and issuesRunOutput. The name golangciLintOutput is true but useless — both are output from golangci-lint.

07Mixed Formatter-Name Typing

High · same concept, two types, one file

FormatterName and string live side by side for formatter names

pkg/constants/config.go:20,26,29

In a single 80-line file, formatter names are typed three different ways: 

// pkg/constants/config.go

var FormattersManagedByBuildFlow = []types.FormatterName{
    "gci", "gofumpt", "goimports",
}                                               // typed

var CoreFormatters = []string{
    "gci", "gofumpt", "goimports",
}                       // untyped, same values

var FormatterOrder = []string{
    "gci", "goimports", "gofumpt", ...
}                       // untyped, same concept

CoreFormatters and FormattersManagedByBuildFlow contain the same formatter names. The first is []string, the second is []FormatterName. Any operation that combines them (set union, ordering) requires a cast that should not be necessary.

Fix All three should be []types.FormatterName. The values are identical, the concept is identical, the types should be too.

08Three Unrelated Config Types

Low · cosmetic, not semantic

Config means three different things in three packages

types.Config · migration.Config · utils.Config

The name Config is overloaded:

  • types.Config — the golangci-lint config file
  • migration.Config — the v1+v2 migration schema
  • utils.Config — retry policy parameters

Go's package qualification makes this legal and unambiguous to the compiler. But it taxes readers who must constantly context-switch on which Config a given reference means. This is the lowest-severity finding because it is purely a naming smell, not a drift risk — but it contributes to the general sense that the data model has no single owner.

Fix Rename utils.Config to RetryPolicy (what it actually is). The other two are genuine config types and remain as-is once the migration hierarchy is unified per section 02.

♦The Vision

What a unified, split-brain-free data model looks like:

One config hierarchy

types.Config is the single source of truth. The migration package embeds it and adds v1-only fields — never redefines shared fields.

One severity vocabulary

finding.Severity everywhere. HealthSeverity deleted. LinterPriority renamed to reflect it is a recommendation level, not a severity.

Brands enforced at the boundary

LinterName on every config field. ConfigPath on ConfigAnalysis. Zero cast sites. The brand is the boundary.

Drift impossible by construction

Shared fields are literally the same type (embedding), not a copy. Adding a field once updates every consumer.

Names that reveal intent

RetryPolicy not utils.Config. lintersListOutput not a second golangciLintOutput. Every name says what it is.

Converters deleted, not maintained

PriorityToSeverity and SeverityFromHealthSeverity disappear when there is one enum. The suspicious Warning→Error mapping is gone or made explicit at the single point of use.

10Validation Layer

With the unified model, invalid states become unrepresentable at three levels:

Type level

[]LinterName on config fields means a typo'd linter name cannot exist as a string in the typed world — it is branded at unmarshal time.

Constructor level

ConfigPath with IsValid() enforced in a constructor means a ConfigAnalysis with an empty path cannot be built.

Enum level

One severity enum means the compiler catches every switch that forgets a case. Today's three-enum system makes exhaustive switches impossible to verify.

Exhaustive switch becomes meaningful

// Today: three enums, converters with
// silent defaults. A new value on
// any enum can be missed.
func PriorityToSeverity(
    p types.LinterPriority,
) finding.Severity {
    switch p {
    case Critical: return SeverityCritical
    case High:     return SeverityError
    case Medium:   return SeverityWarning
    case Optional: return SeverityInfo
    default:       return SeverityInfo
    }                            // silent!
}
// Unified: one enum, no converter.
// Adding a value forces every switch
// to handle it or fail to compile.
// No default → compiler enforces
// exhaustiveness.
func levelToSeverity(
    l RecommendationLevel,
) Severity {
    switch l {
    case LevelRequired:
        return SeverityCritical
    case LevelRecommended:
        return SeverityError
    case LevelOptional:
        return SeverityWarning
    case LevelNiche:
        return SeverityInfo
    }
    // no default — compiler-verified
}

11Decision Log

Why each choice was made, with rejected alternatives:

Embed canonical types in migration (vs alias)

Chose embedding because v1 legitimately has fields v2 does not (EnableAll, Fast, ExcludeRules at issues. level). A type alias would force v2 to carry v1 baggage. Embedding lets shared fields be identical while v1-only fields stay explicit.

Rejected: type alias (type Linters = types.LintersConfig) — works for shared fields but cannot add v1-only fields without a wrapper, which is just embedding with extra steps.

Delete HealthSeverity (vs keep and align)

Chose deletion because its three values (Critical, Warning, Info) are a strict subset of finding.Severity. Keeping it requires a permanent converter that can drift. The only cost is that finding.Severity has an Error level with no health equivalent — acceptable, since health checks producing errors rather than warnings is the correct escalation.

Fix the Warning→Error mapping (vs preserve it)

Chose to fix (Warning → SeverityWarning) because there is no comment explaining the escalation and no test asserting it is intentional. If it is intentional (treat all config health warnings as CI errors), that decision belongs in the caller, not buried in a converter named SeverityFromHealthSeverity that implies a faithful mapping.

Brand config fields with LinterName (vs leave as string)

Chose branding because YAML/JSON unmarshaling into a branded string type is zero-cost (Go handles the underlying type automatically), and it eliminates 8+ cast sites. The brand was always intended to be used here — the doc comment literally says "prevent typos in linter names."

Rejected: runtime validation in the brand (e.g., a ValidLinterName constructor that checks against a registry) — would require the registry to be available at unmarshal time and creates a cycle. The brand gives compile-time distinction; runtime validity stays in the analyzer.

Use ConfigPath on ConfigAnalysis (vs delete ConfigPath)

Chose to use it rather than delete it because the type carries IsValid(), which is meaningful validation for a path. Deleting the brand loses that; using it enforces it. The fix is strictly better than the status quo (brand defined but ignored).

12Migration Roadmap

Ordered by impact and reversibility. Each step is independently shippable.

1

Fix the Warning→Error mapping

In pkg/finding/helpers.go:62, change HealthSeverityWarning → SeverityError to SeverityWarning. One line. Verify with the converter test. If CI breaks, the escalation was intentional and should be documented at the call site instead. Lowest risk, highest signal.

2

Brand LinterName on config fields

Change LintersConfig.Enable/Disable to []LinterName. Delete the 8 types.LinterName(x) casts. Run just test — YAML round-trip is unaffected. This is the highest-value-per-line change in the whole audit.

3

Unify formatter-name typing in constants

Change CoreFormatters and FormatterOrder to []types.FormatterName in pkg/constants/config.go. Same-file, low blast radius.

4

Use ConfigPath on ConfigAnalysis

Change the field type, update consumers in pkg/finding and pkg/report to take types.ConfigPath. Add an IsValid() guard where ConfigAnalysis is constructed.

5

Delete HealthSeverity, adopt finding.Severity

Replace HealthSeverity usages in pkg/types/validation.go with finding.Severity. Delete SeverityFromHealthSeverity. Update ConfigHealth and its consumers. Medium blast radius — touches the health-check subsystem.

6

Embed types in migration package

The largest change. Convert migration.Config to embed types.Config, keeping only v1-only fields explicit. Update the migrator and its tests. This is the highest-risk step but also eliminates the largest drift surface (11 types).

7

Rename for clarity

utils.Config → RetryPolicy. Rename the two golangciLintOutput structs. Optionally rename LinterPriority → RecommendationLevel. Pure renames, no behavior change.

13Conclusion

"Every split-brain is a place where a future change can land on the wrong copy and silently pass type-checking. The compiler cannot protect a model that has been forked — only the removal of the fork restores the guarantee."

This codebase has a strong typed core (LinterName, Set[T], ConfigFormat) that demonstrates the team values type safety. The split-brains are not a failure of discipline but a consequence of three independent merges — the migrator, the branding effort, and the go-finding integration — each of which introduced a parallel structure that was never reconciled. Reconciling them is a sequence of small, shippable steps, not a rewrite. The roadmap above is ordered so the highest-value changes come first and the riskiest come last, after the cheaper drift surfaces are already closed.
