DATA MODEL REVIEW · 2026-07-26

Is the data model superb?

A first-principles review of 196 struct types across 19 packages. The model is B+ today: branded types (LinterName, FormatterName) and a generic Set[T] show intent, and the error model is genuinely excellent. But branded types are applied to only ~half the codebase, a duplicate Config splits the domain, and map[string]any settings bypass the type system in the hottest paths.

01Problem catalog

Seven problems, graded by severity and systemicity. Two are critical; the rest are medium-to-low debt.

Critical · systemic

P1 — Split-brain: two Config types for one domain

pkg/types/config_types.go:5 & pkg/migration/config_types.go:10

types.Config (v2-only, typed sub-structs, map[string]any settings) and migration.Config (v1+v2, *bool tri-state, different names) represent the same concept with incompatible shapes. Seven sub-structs are fully duplicated (RunConfig/Run, LintersConfig/Linters, etc.) and exclusion rules are triplicated (ExclusionRuleConfig, ExclusionRule, ExcludeRule). Every conversion between them is hand-written, error-prone glue. 

// types/config_types.go — the "real" Config
type Config struct {
    Version string          `yaml:"version"`
    Run     RunConfig      `yaml:"run"`
    Linters LintersConfig  `yaml:"linters"`
    // ...
}

// migration/config_types.go — the "other" Config
type Config struct {
    Version string          `yaml:"version"`
    Run     Run            `yaml:"run"`
    Linters Linters        `yaml:"linters"`
    ExcludeDirUseDefault *bool  // tri-state: nil/true/false
    // ...
}
Fix: unify on types.Config v1 support is maintenance-only (0 live v1 configs). Make migration.Config a thin unmarshaling shim that normalizes v1→v2 into types.Config, then delete the duplicate sub-structs. The *bool tri-state fields collapse into an enum of {Default, Enable, Disable}.
Critical · systemic

P2 — Branded types applied to only half the codebase

pkg/types/config_types.go:44-65 · pkg/audit/ledger.go:63 · pkg/policy/policy.go:40 · pkg/finding/golangci_lint.go:14

LinterName and FormatterName exist as branded types, but the core config structs still use raw []string for linter and formatter lists. The audit ledger, policy sidecar, finding issue, and report types also use string where the branded type should be. This defeats half the purpose of having branded types — a typo like "gosec" vs "GoSec" is not caught at compile time in the config path. 

// config_types.go — branded type exists, but fields ignore it
type LintersConfig struct {
    Enable  []string  // should be []types.LinterName
    Disable []string  // should be []types.LinterName
}

// audit/ledger.go — Entry.Linter is plain string
type Entry struct {
    Linter string  // should be types.LinterName
}
Fix: propagate branded types to the boundary Change Enable/Disable to []LinterName / []FormatterName. YAML/JSON tags still serialize to strings, but the Go API becomes typo-proof. The ~20 affected sites are mechanical changes.
High · systemic

P3 — map[string]any bypasses the type system in hot paths

pkg/types/config_types.go:36,47,87 · pkg/linter/fixer_config.go · pkg/config/merger_*.go

OutputConfig.Formats, LintersConfig.Settings, and FormattersConfig.Settings are map[string]any. Every consumer (clone.go, merger_helpers.go, fixer_config.go, settings_validator.go) does repeated .(map[string]any) type assertions. The SettingsConverter pattern with typed structs (ExhaustructSettings, GosecSettings, etc.) is excellent for defaults, but user-supplied settings still flow through the untyped map.

Tradeoff to acknowledge map[string]any is intentional here — it preserves round-trip safety for arbitrary user YAML keys the tool doesn't know about. The SettingsConverter structs cover the known defaults. A full fix (typed settings registry) is high-effort; the current split is a defensible compromise, but the type assertions should be centralized behind one accessor.
High · central type

P4 — Config has no constructor — invalid states compile

pkg/types/ (no NewConfig) · validation.go:32 ValidateConfig is opt-in

&types.Config{} is a valid Go value that represents an invalid golangci-lint config (no version, no timeout). ValidateConfig() exists but is never called automatically — callers must remember. Tests construct partial configs via literals (&types.Config{Version: "2"}) that would fail validation. The production default-config factory (newDefaultConfig) lives in the wrong package (pkg/config, not pkg/types). 

// Today: anyone can build an invalid Config
cfg := &Config{}  // compiles, but Version="" and Run.Timeout=""

// Target: constructor enforces invariants
func NewConfig(opts ...ConfigOption) *Config {
    c := &Config{Version: ConfigVersionV2, Run: RunConfig{Timeout: DefaultTimeout}}
    for _, o := range opts { o(c) }
    return c  // always valid
}
Fix: add NewConfig to pkg/types A functional-options constructor that sets mandatory defaults (Version, Timeout) and moves newDefaultConfig from pkg/config into pkg/types. Keep ValidateConfig as defense-in-depth.
Medium · systemic

P5 — Version is a raw string everywhere

types.go:149,95,117 · analyzer.go:30 · migration/config_types.go:15

There is no branded Version type. Config.Version, LinterInfo.Since, LinterReplacement.MinVersion, Analyzer.detectedVersion are all string. Semver comparisons (semver.Compare) happen on raw strings, and the canonical version constant ConfigVersionV2 = "2" is an untyped string. A type Version string with a Compare method would centralize the semver logic and prevent passing arbitrary strings where a version is expected.

Medium · scoped

P6 — *bool tri-state in migration types

pkg/migration/config_types.go:11-13,91,100-102

Seven *bool fields represent v1-era deprecation flags where nil, true, and false are three distinct states. This is the standard Go tri-state pattern, but it is a known smell — an explicit type TriState int enum (Default/Enabled/Disabled) would be self-documenting and avoid nil-deref risk. Acceptable while v1 migration remains maintenance-only.

Low · design smell

P7 — settingsToMap round-trips through YAML at runtime

pkg/constants/linter_settings.go:19-33

settingsToMap converts typed settings structs to map[string]any by marshaling to YAML then unmarshaling to a map. This is runtime reflection where compile-time is possible, and it panics on marshal failure (which is theoretically impossible for these static structs, but the panic signals a design gap). A generated or hand-written ToMap() per struct would be faster and panic-free, at the cost of verbosity.

02The vision

A data model where invalid states are unrepresentable. One Config. Branded types at every boundary. Settings that are typed end-to-end. Constructors that enforce invariants at creation. This is achievable incrementally — the existing patterns (branded types, enums, SettingsConverter) are the foundation; they just need to be propagated consistently.

The guiding question For every field, ask: "Could I construct this with a value that violates a business rule and still compile?" If yes, the type is too weak. Today, Enable []string fails this test. Enable []LinterName passes it.

03Redesigned model

Target type definitions for the highest-impact fixes. Each uses Go's type system to make misuse a compile error.

1. Branded version type

// pkg/types/version.go
type Version string

const ConfigVersionV2 Version = "2"

func (v Version) Valid() bool {
    return v == ConfigVersionV2
}

func ParseVersion(s string) (Version, error) {
    v := Version(s)
    if !v.Valid() { return "", ErrVersionInvalid }
    return v, nil
}

2. Branded config path

type ConfigPath string

func (p ConfigPath) Ext() ConfigFormat {
    switch filepath.Ext(string(p)) {
    case ".yml", ".yaml": return ConfigFormatYAML
    case ".toml":         return ConfigFormatTOML
    case ".json":         return ConfigFormatJSON
    default:           return ConfigFormatYAML
    }
}

3. Config with branded fields + constructor

type LintersConfig struct {
    Enable  []LinterName  `yaml:"enable,omitempty"`
    Disable []LinterName  `yaml:"disable,omitempty"`
    // ...
}

type FormattersConfig struct {
    Enable  []FormatterName  `yaml:"enable,omitempty"`
    Disable []FormatterName  `yaml:"disable,omitempty"`

// Constructor: impossible to build an invalid Config
func NewConfig(opts ...ConfigOption) *Config {
    c := &Config{
        Version: ConfigVersionV2,

    for _, o := range opts { o(c) }

04How invalid states become unrepresentable

The combination of branded types + constructors + enums creates a layered defense. Each layer catches a class of error that today requires runtime validation.

Error class Today (runtime) After (compile-time)
Typo in linter name Silently ignored or runtime warning []LinterName — string still allowed, but typed at API boundary
Config missing version ValidateConfig catches (if called) NewConfig() always sets it
Passing a path where version expected No protection — both are string Version vs ConfigPath — different types
Unknown priority value Already typed (LinterPriority enum) No change needed
Arbitrary settings keys map[string]any accepts anything Typed structs for known; map retained for unknown (intentional)

05Migration roadmap

Ordered by impact-to-effort ratio. Steps 1–3 are mechanical and high-value.

1

Propagate LinterName/FormatterName to config structs

Change Enable/Disable in LintersConfig and FormattersConfig to []LinterName / []FormatterName. Update audit Entry.Linter, policy map keys, and finding types. ~20 sites, all mechanical. YAML serialization is unaffected.

2

Add NewConfig constructor to pkg/types

Functional-options constructor with mandatory defaults. Move newDefaultConfig from pkg/config to pkg/types. Update test literals to use the constructor.

3

Brand Version and ConfigPath

type Version string and type ConfigPath string with helper methods. Centralize semver comparison behind Version.Compare.

4

Unify the duplicate Config type

Collapse migration.Config into a v1→v2 normalizing shim over types.Config. Delete the 7 duplicate sub-structs and the triplicated exclusion rules. This is the largest effort but the highest architectural payoff.

5

Centralize map[string]any access behind one accessor

Extract a SettingsMap wrapper type with typed getters (GetString, GetSlice) that centralizes the type assertions and returns typed errors instead of panicking. Keeps round-trip safety, removes scattered .(map[string]any) assertions.
