ARCHITECTURE REVIEW · 2026-07-26

Is the architecture superb?

A modular Go CLI (16.6k LOC, 19 packages) that auto-configures golangci-lint. Reviewed for scalability, modularity, service orientation, and composability. The dependency graph is a clean DAG with zero cycles; the weaknesses are in coupling depth and concern conflation, not structure.

00Verdict

Yes — with one caveat. This is a genuinely well-architected codebase: a strict layered DAG, disciplined interface segregation, wire-format decoupling, and no god files. It would score an A if not for a cluster of coupling issues centered on pkg/linter reaching down into pkg/config, and a split-brain duplicate Config type between pkg/types and pkg/migration. Fix those two things and it is among the cleanest Go CLIs of this size.

The bottom line The architecture is scalable and modular today. The single highest-leverage change is inverting the linter → config dependency so the fixing engine depends only on a port (interface), not on the concrete loader. That one move unlocks composability for the finding pipeline and dissolves the pkg/client god-package.

◆What's already excellent

Eight patterns here are worth keeping and copying. These are the load-bearing structure that makes the codebase maintainable.

+
Zero import cycles — verified acyclic DAG Every package edge was checked. types, errors, audit, policy, version, detection are pure leaves. The graph flows strictly top-down: internal/cli → domain → leaves.
+
Interface Segregation done right Six narrow sub-interfaces in pkg/types (ConfigReader, ConfigWriter, ConfigDiscoverer, ConfigValidator, ConfigInspector, ConfigCreator) composed into one ConfigLoader. Consumers define their own minimal local interfaces (fixerConfigLoader, presetConfigLoader). Textbook ISP.
+
Wire-format decoupling from report types golangciLinterEntry / golangciFormatterEntry in analyzer.go match golangci-lint's exact JSON shape (capitalized wrapper keys, lowercase field keys) and convert to tag-free LinterInfo report types. Avoids the json/v2 case-sensitivity conflict cleanly.
+
Filesystem abstraction for testability The FS interface (loader.go:64) with osFS default + NewLoaderWithFS injection lets config loading be tested without touching disk. Mature pattern.
+
Best-effort audit ledger with safe default audit.Recorder interface + NoopRecorder zero-value default means the Fixer is safe to construct without a ledger, and recording failures never block a run. Small, composable, exemplary.
+
No god files Only one file exceeds 500 lines (linter_settings_generated.go, ~1692 lines) and it is code-generated from a JSON schema. Every hand-written file is <460 lines. Functions are small and single-purpose.
+
Manual DI with safe defaults NewFixer wires NoopRecorder and constructs a FormatterManager internally; SetLedger / SetPolicy mutate later. No DI framework, no magic — just clear constructors.
+
Strong test ratio (0.79 test:source) 13,170 lines of BDD tests (Ginkgo+Gomega) against 16,605 source lines. Every package has its own suite_test.go. Benchmarks, fuzz tests, and golden snapshots exist where they matter.

01The dependency graph

The full internal import graph. Arrows point from importer to imported. The layering is clean; the concerns are in depth, not direction.

internal/cli → config → constants → types (leaf) → errors → types (leaf) → utils → errors → linter → config · audit · detection · gogenfilter · policy → finding → linter → config (transitive) → client → config + linter (god-package) → migration · report · ui · version (clean leaves/branches)
Read this carefully The three red edges (linter, finding, client) all stem from one root cause: the fixing engine depends on the concrete config I/O package. Fix that, and the finding and client packages untangle for free.

02Findings

Six issues, ordered by impact. None are structural emergencies — they are coupling debts that compound.

High impact · coupling

pkg/linter imports pkg/config — engine bound to I/O

pkg/linter/fixer.go:14 · fixerConfigLoader · pkg/linter/fixer_config.go:10

The Fixer (the fixing engine) takes a fixerConfigLoader interface for tests, but production wiring in commands.go passes a concrete *config.Loader. More importantly, fixer_config.go directly imports pkg/config for helpers. This conflates "knows how to fix a config" with "knows how to load/save a config from disk." The engine should depend on a port, never on the adapter.

Fix: invert the dependency Move fixer_config.go's config helpers behind an interface the Fixer already owns (fixerConfigLoader), or move those helpers into pkg/linter. The concrete config.Loader should be the only thing that imports pkg/config from outside, injected at the CLI boundary.
High impact · split brain

Duplicate Config type across pkg/types and pkg/migration

pkg/types/config_types.go:5 vs pkg/migration/config_types.go:10

Two completely different Config structs represent the same domain concept. types.Config is v2-only with typed sub-structs; migration.Config is v1+v2 with *bool tri-state fields and different sub-struct names (Run vs RunConfig, Linters vs LintersConfig). Data must be manually converted between them. This is the single largest architectural debt — covered in depth in the companion data model review.

Fix: unify on types.Config The v1 support is maintenance-only (0 live v1 configs). Collapse migration.Config into a thin unmarshaling shim over types.Config, or extract a shared configschema package both can reference.
Medium impact · god-package

pkg/client is a composition root masquerading as a library

pkg/client/client.go:9,11

pkg/client imports both config and linter directly. It has no single responsibility — it glues the loader to the analyzer. That is the job of the CLI layer (internal/cli), not a public package. A library consumer who imports pkg/client transitively pulls in the entire stack.

Fix: dissolve or rename Either fold pkg/client into internal/cli (it is wiring, not a library), or give it a focused responsibility (e.g. a Facade with a single Configure() entry point) that hides the internal packages it composes.
Medium impact · transitive coupling

pkg/finding transitively depends on pkg/config via pkg/linter

pkg/finding/detector.go:9 → pkg/linter → pkg/config

The finding model (converters for SARIF/JSON output) transitively pulls in the entire config+linter stack. A finding converter should not need to know how configs are loaded from disk. This blocks pkg/finding from being a reusable, standalone library — it currently drags in ~8 packages.

Fix: finding should depend only on types If finding needs linter metadata, pass it in as a parameter (a []LinterInfo or a priority lookup function), not by importing the analyzer. This makes the finding pipeline a clean leaf.
Medium impact · shared state

Package-level mutable CLI flags

internal/cli/commands.go:25-39 · cmd_configure.go:19

Twelve global var flags (configPath, dryRun, verbose, etc.) plus detectedExtraFormatters are package-level mutable state. This prevents concurrent command execution, complicates isolated testing, and makes flag plumbing implicit. The migrateFlags struct in commands.go is a half-step toward fixing this but copies the globals rather than replacing them.

Fix: per-command flag structs Pass flag values through a CommandBuilder options struct (the pattern already exists for presetConfigLoader). Eliminate the package-level var block entirely.
Low impact · housekeeping

Type-alias re-exports in pkg/config create import ambiguity

pkg/config/loader.go:51-61

The type Config = types.Config aliases (and 8 siblings) let callers write either config.Config or types.Config for the same type. This is backward-compat scaffolding that now creates two valid import paths to every config type. It makes grep-based navigation ambiguous and signals the package boundary is soft.

03Target architecture

If the six findings were resolved, the dependency graph would flatten. The fixing engine becomes a pure consumer of ports; the finding pipeline becomes a standalone leaf; the CLI is the only composition root.

internal/cli (composition root — the only place that imports concrete adapters) ├ config.Loader (adapter: implements ConfigReader/Writer) ├ linter.Fixer + Analyzer (engine: depends only on types + ports) ├ finding.Converter (leaf: depends only on types) └ audit · policy · detection · migration (leaves)
This is the target One composition root, clean ports, no engine depends on an adapter. The audit Recorder interface is already the template for how every other boundary should look.

04Recommended roadmap

Ordered by leverage. Steps 1–2 unlock the rest.

1

Invert the linter→config dependency

Make pkg/linter depend only on types + interfaces it owns. Move config helpers from fixer_config.go behind fixerConfigLoader. Highest leverage — unblocks steps 2 and 3.

2

Decouple pkg/finding from pkg/linter

Pass linter metadata as parameters to finding converters instead of importing the analyzer. Finding becomes a clean, reusable leaf.

3

Dissolve pkg/client into internal/cli

It is wiring, not a library. Once steps 1–2 land, its remaining glue belongs in the composition root.

4

Unify the duplicate Config type

Collapse migration.Config into a shim over types.Config. See the data model review for the full type-level redesign.

5

Remove global CLI flags & alias re-exports

Per-command flag structs; delete the type X = types.X aliases once callers use the canonical types. path.
