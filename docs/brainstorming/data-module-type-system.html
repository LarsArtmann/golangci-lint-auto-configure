What Is Already Excellent Strengths

1. Nominal Typing for Domain Names

The project already uses distinct types for domain names, preventing accidental interchange:

pkg/types/types.go
// LinterName is a strongly-typed linter name to prevent typos.
type LinterName string

func (ln LinterName) String() string {
    return string(ln)
}

// FormatterName is a strongly-typed formatter name to prevent typos.
type FormatterName string

Why this matters: You cannot accidentally pass a FormatterName where a LinterName is expected. The compiler rejects it. This is the right instinct — but the project stops short of taking this to its logical conclusion.

2. Generic Result[T] — DELETED on 2026-06-05

Status: pkg/types/result.go was deleted. All functions now return idiomatic (T, error). The wrapper added indirection with zero benefit — every call site immediately unwrapped with .Get(). The file was 54 lines of boilerplate wrapping values that were immediately unwrapped.

3. Generic Set[T comparable] — No Ad-Hoc Map Logic

pkg/types/set.go
// Set is a generic set of comparable values with O(1) lookups.
type Set[T comparable] map[T]struct{}

func (s Set[T]) Contains(item T) bool { ... }
func (s Set[T]) Union(other Set[T]) Set[T] { ... }

Why this matters: Replaces every map[string]struct{} with a typed abstraction. The codebase already does this — it just hasn't extended the pattern to other collections.

4. Deep Clone with Generic Helpers

pkg/types/clone.go
func cloneSlice[T any](src []T) []T {
    if src == nil { return nil }
    cp := make([]T, len(src))
    copy(cp, src)
    return cp
}

Why this matters: Using a generic cloneSlice[T any] is exactly right. The pattern is solid — it just needs to be extended to map cloning and beyond.

5. Custom Error Types with Unwrap()

pkg/errors/errors.go
type ConfigError struct {
    Message string
    Path    string
    Cause   error

func (e *ConfigError) Unwrap() error { return e.Cause }

Why this matters: Proper use of errors.As, wrapped chains, and sentinel errors. This is production-grade Go error handling. The only gap is that these types don't use generics for the domain-error base pattern.

The Gaps — Where Illegal States Live Weaknesses

1. Stringly-Typed Constants — Six Maps, Zero Coherence

The linter metadata is scattered across six separate maps in pkg/constants/:

pkg/constants/linter_priorities.go, linter_reasons.go, rules.go, presets.go, formatter_data.go, version.go
// linter_priorities.go
var LinterPriorities = map[LinterName]LinterPriority{...}

// linter_reasons.go
var LinterReasons = map[LinterName]string{...}

// rules.go
var DeprecatedLinters = map[LinterName]LinterReplacement{...}

// Nothing ensures every linter has a priority AND a reason AND is in the registry.
// A linter can exist in one map but not another, and the compiler is silent.

The problem: If you add gosec to LinterPriorities but forget to add it to LinterReasons, the code still compiles. The failure is deferred to runtime — when a user sees an empty reason string in output. The Go type system has zero visibility into this.

2. map[string]any — The Billion-Dollar Mistake in Linter Settings

pkg/types/types.go
type LintersConfig struct {
    Enable   []string
    Disable  []string
    Default  string
    Settings map[string]any   // <-- Completely untyped
    ...
}

The problem: Every linter's settings are map[string]any. When the fixer reads cfg.Linters.Settings["funlen"], it returns any. Casting to the wrong struct panics at runtime. There's no autocomplete. No compiler help. This is the exact pattern that makes Go feel "less typed" than it needs to be.

3. Count Fields That Must Stay in Sync

pkg/types/types.go
type ConfigAnalysis struct {

    HighValueCount   int   // Must == len(linters with High priority)
    MediumValueCount int   // Must == len(linters with Medium priority)

The problem: Five fields that are pure derivatives of the Recommendations and DeprecatedLinters slices. They can drift out of sync if a caller mutates the slice but forgets to update the count. The type system sees five independent ints — it has no idea they're supposed to be coherent.

Proposed Improvements — Toward Type-Safe Perfection Target State

Core Principle: Make illegal states unrepresentable. Every gap above should become a compile-time error, not a runtime bug. Generics are the tool that gets us there.

1. Sealed Name Interface + Generic Priority[N]

Current: Parallel types, no relationship
type LinterPriority int
type FormatterPriority int

// Can accidentally construct:
rec := LinterRecommendation{
    Name:     "gosec",
    Priority: FormatterPriorityHigh,  // <-- Compiles! Wrong!
}
Proposed: Generic Priority tied to Name
// Sealed interface — only types in this package can implement it.
type Name interface {
    ~string
    sealed()
}

func (LinterName) sealed()   {}
func (FormatterName) sealed() {}

// Priority is generic over the name type it applies to.
type Priority[N Name] int

type LinterPriority   = Priority[LinterName]
type FormatterPriority = Priority[FormatterName]

type Recommendation[N Name] struct {
    Name     N
    Priority Priority[N]  // Tied to the same name type!
    Reason   string
}

type LinterRecommendation   = Recommendation[LinterName]
type FormatterRecommendation = Recommendation[FormatterName]

// Now this is a COMPILE ERROR:
rec := LinterRecommendation{
    Name:     "gosec",
    Priority: FormatterPriorityHigh,  // Cannot assign FormatterPriority to LinterRecommendation!
}

Impact: The compiler now enforces that a LinterRecommendation can never hold a FormatterPriority. This is the difference between "don't do that" (docs) and "literally impossible" (types).

2. Generic Catalog[E, N] — Replace Six Maps with One Type

Current: Six disconnected maps
// Scattered across 6 files. No compile-time guarantee of completeness.
var LinterPriorities   map[LinterName]LinterPriority
var LinterReasons      map[LinterName]string
var DeprecatedLinters  map[LinterName]LinterReplacement
var LinterMinVersions  map[LinterName]string

// Looking up a linter requires N map accesses:
priority, ok := LinterPriorities[name]
reason, ok2 := LinterReasons[name]
// What if ok is true but ok2 is false? Silent bad output.
Proposed: Single Entry + Catalog
// Entry is the COMPLETE metadata record for a tool.
// Every linter has exactly one Entry. Every field is present.
type Entry[N Name] struct {
    Name        N
    Priority    Priority[N]
    Reason      string
    Deprecated  *Replacement[N]  // nil means "not deprecated"
    MinVersion  string          // "" means "no minimum version"
    Groups      []string
    Fast        bool
    AutoFix     bool
    Since       string
    OriginalURL string
}

type LinterEntry = Entry[LinterName]

// Catalog is a type-safe lookup table with a guaranteed-complete init check.
type Catalog[E any, N Name] struct {
    entries map[N]E
}

func NewCatalog[E any, N Name](
    entries []E,
    nameFn func(E) N,
) *Catalog[E, N]

func (c *Catalog[E, N]) Get(name N) (E, bool)
func (c *Catalog[E, N]) MustGet(name N) E
func (c *Catalog[E, N]) Names() Set[N]
func (c *Catalog[E, N]) FilterByPriority(p Priority[N]) []E

// Usage:
catalog := NewCatalog(AllLinterEntries, func(e LinterEntry) LinterName { return e.Name })
entry, ok := catalog.Get("gosec")
// entry has Priority, Reason, Deprecated, MinVersion — all in one lookup.

Impact: Adding a new linter now means adding one struct literal to one slice. The compiler enforces that every field is populated. No more silent omissions across six maps. Plus, you get rich query methods (FilterByPriority, Names, etc.) for free.

3. Sealed LinterSetting Interface — Type-Safe Config Settings

Current: map[string]any
type LintersConfig struct {
    Settings map[string]any
}

// Runtime panic if you get the type wrong:
raw := cfg.Linters.Settings["funlen"]
settings := raw.(FunlenSettings)  // Panics if it's actually GocycloSettings!
Proposed: Sealed Interface + Registry
// Sealed — only types in this package can implement it.
type LinterSetting interface {
    linterSetting()
    Validate() error
}

type FunlenSettings struct {
    Lines      int `yaml:"lines"`
    Statements int `yaml:"statements"`
}
func (FunlenSettings) linterSetting() {}
func (s FunlenSettings) Validate() error {
    if s.Lines < 0 {
        return fmt.Errorf("funlen.lines must be >= 0")
    }
    return nil
}

type GocycloSettings struct {
    MinComplexity int `yaml:"min-complexity"`
}
func (GocycloSettings) linterSetting() {}

// Registry maps linter names to their typed settings.
var KnownSettings = map[LinterName]LinterSetting{
    "funlen":   FunlenSettings{Lines: 80, Statements: 50},
    "gocyclo":  GocycloSettings{MinComplexity: 10},
}

// For linters without known typed settings, fall back:
type RawSettings map[string]any
func (RawSettings) linterSetting() {}
func (r RawSettings) Validate() error { return nil }

Impact: Every linter setting is either a known typed struct (with IDE autocomplete and compile-time safety) or an explicit RawSettings fallback. The Validate() method means invalid values are caught at parse time, not runtime.

4. Validated[T] — Parse, Don't Validate

Current: Validate after construction
// Config can exist in an invalid state at any time.
func AnalyzeConfig(ctx, path) (*ConfigAnalysis, error) {
    cfg, err := loader.LoadConfig(path)
    if err != nil { return nil, err }

    // What if cfg.Version is empty? Or negative concurrency?
    // The function proceeds with an invalid Config.
    ...
}

// Callers must remember to validate before using.
if err := ValidateConfig(cfg); err != nil { ... }
Proposed: Validated[T] proof type
// Validated wraps a value that has passed validation.
// The zero value is INVALID — you MUST use Validate().
type Validated[T any] struct {
    value T
    valid bool
}

func Validate[T any](v T, fn func(T) error) (Validated[T], error) {
    if err := fn(v); err != nil {
        return Validated[T]{}, err
    }
    return Validated[T]{value: v, valid: true}, nil
}

func (v Validated[T]) Value() T {
    if !v.valid { panic("Validated.Value called on unvalidated value") }
    return v.value
}

// Functions that REQUIRE a valid config take this type:
func AnalyzeConfig(ctx, cfg Validated[Config]) (*ConfigAnalysis, error) {
    // cfg.Value() is guaranteed valid here. No runtime checks needed.
}

Impact: Functions that need a valid config now demand Validated[Config] in their signature. You cannot pass a raw Config — the compiler rejects it. This is "parse, don't validate" at the type level.

5. Generic PriorityCounts[N] — Derived Data, Guaranteed Coherent

Current: Five independent int fields
type ConfigAnalysis struct {
    CriticalCount    int
    HighValueCount   int
    MediumValueCount int
    OptionalCount    int
    DeprecatedCount  int
}

// If someone mutates Recommendations but forgets to update counts:
analysis.LinterRecommendations = append(analysis.LinterRecommendations, rec)
// CriticalCount is now stale — a silent data inconsistency.
Proposed: Derived PriorityCounts
// PriorityCounts is a map from priority to count.
// It is always coherent because it is derived, not stored.
type PriorityCounts[N Name] map[Priority[N]]int

type Analysis[N Name] struct {
    ConfigPath       ConfigPath
    Enabled          *Catalog[Entry[N], N]
    Disabled         *Catalog[Entry[N], N]
    Recommendations  []Recommendation[N]
    Deprecated       []Entry[N]
}

// Counts are computed on demand — always correct:
func (a *Analysis[N]) Counts() PriorityCounts[N] {
    counts := make(PriorityCounts[N])
    for _, rec := range a.Recommendations {
        counts[rec.Priority]++
    }
    return counts
}

func (a *Analysis[N]) CountByPriority(p Priority[N]) int {
    return a.Counts()[p]
}

// No fields to get out of sync. Counts are a pure function of Recommendations.

Impact: No more stale counts. The count is always a pure function of the source data. Mutating Recommendations automatically updates Counts() on the next call. The type system prevents assigning a formatter priority count to a linter analysis.

6. Railway-Oriented Result[T] with AndThen / Map NOT APPLIED — DELETED

Current: Manual error branching
func AnalyzeConfig(ctx, path) (*ConfigAnalysis, error) {
    result := analyzer.FindBinary(ctx)
    if result.IsError() {
        _, err := result.Get()
        return nil, err
    }

    result2 := analyzer.CheckVersion(ctx)
    if result2.IsError() {
        _, err := result2.Get()
        return nil, err
    }

    // ... and so on. Verbose, error-prone, deeply nested.
}
Proposed: Fluent railway chain
func (r Result[T]) AndThen[U any](fn func(T) Result[U]) Result[U] {
    if r.err != nil { return Err[U](r.err) }
    return fn(r.value)
}

func (r Result[T]) Map[U any](fn func(T) U) Result[U] {
    if r.err != nil { return Err[U](r.err) }
    return Ok(fn(r.value))
}

func (r Result[T]) UnwrapOr(fallback T) T {
    if r.err != nil { return fallback }
    return r.value
}

// Usage:
result := Ok(path).
    AndThen(analyzer.FindBinary).
    AndThen(analyzer.CheckVersion).
    AndThen(func(_) Result[*ConfigAnalysis] {
        return analyzer.AnalyzeConfig(ctx, path)
    })

analysis, err := result.Get()
// All errors short-circuit automatically. Zero nesting.

Status: This proposal was not implemented. Instead, Result[T] was deleted entirely. The analyzer pipeline now uses plain (T, error) returns — no wrapping, no unwrapping, no indirection. Go's native error handling is exactly what we need.

7. Sealed Sum Type for Fix Outcomes

Current: String + int counts
type MigrationResult struct {
    FixesApplied int
    Message      string   // <-- Caller must parse this string
    NextSteps    []string
    Error        error
}

// CLI layer wants to know: "which linters were enabled?"
// It must re-parse the config or regex the Message string.
Proposed: Sealed sum type
// FixOutcome is a sealed sum type — exactly one variant holds.
type FixOutcome interface { fixOutcome() }

type NoChangesNeeded struct{}
func (NoChangesNeeded) fixOutcome() {}

type DryRun struct {
    WouldEnable  []LinterName
    WouldDisable []LinterName
    WouldReplace map[LinterName]LinterReplacement
}
func (DryRun) fixOutcome() {}

type Applied struct {
    EnabledLinters    int
    EnabledFormatters int
    ReplacedDeprecated int
    ExcludedGenerated  int
    Path              ConfigPath
    EnabledNames      []LinterName  // <-- Structured!
}
func (Applied) fixOutcome() {}

type FixResult struct {
    Outcome FixOutcome
    Config  *Config  // nil when dry-run or no changes
}

// Caller uses a type switch for full structured access:
switch out := result.Outcome.(type) {
case Applied:
    for _, name := range out.EnabledNames {
        logger.Infof("Enabled %s", name)
    }
case DryRun:
    for _, name := range out.WouldEnable {
        logger.Infof("Would enable %s", name)
    }
case NoChangesNeeded:
    logger.Info("No changes needed")
}

Impact: The CLI layer now has structured access to every piece of fix metadata. No string parsing. No guesswork. The compiler verifies that every outcome variant is handled (if you use a type switch without a default, the compiler nags you about exhaustiveness in practice).

Key Strategy: Type Aliases + Gradual Deprecation

At each phase, introduce the new generic type alongside the old one. Use type aliases to maintain compatibility:

Compatibility Pattern
// New generic type (internal implementation)
type recommendation[N Name] struct {
    Name     N
    Priority Priority[N]
    Reason   string
}

// Old exported type is now an alias — zero breakage for callers
type LinterRecommendation = recommendation[LinterName]
type FormatterRecommendation = recommendation[FormatterName]

This means callers who use LinterRecommendation see no change. But new code can use recommendation[LinterName] directly, and generic functions can operate over recommendation[N] for any name type.

Design Philosophy Principles

1. Nominal over Structural: LinterName and FormatterName are both ~string, but they are not interchangeable. The type system should enforce this. A function that takes LinterName should never accept FormatterName — even if the runtime value happens to be the same string.

2. Generic over Duplicated: LinterPriority and FormatterPriority share the exact same semantics (ordered levels). They should be one generic type Priority[N], not two parallel types. The same applies to LinterRecommendation / FormatterRecommendation, ConfigAnalysis's linter/formatter fields, and so on.

3. Derived over Stored: If a field can be computed from other fields, don't store it. CriticalCount should not exist as a field — it should be a method. This eliminates an entire class of consistency bugs.

4. Sealed over Open: If only specific types in your package should implement an interface, make it sealed (unexported method). This prevents external packages from inventing new LinterSetting implementations that your YAML loader doesn't know about.

5. Explicit over Implicit: Validated[T] is better than "validate before use" conventions. Types should carry intent — but wrappers that are immediately unwrapped (like the deleted Result[T]) add indirection without value. Prefer idiomatic Go when it is already explicit enough.

6. Parse, Don't Validate: A function should receive data that is already proven valid in its type, not validate it after receiving it. AnalyzeConfig(cfg Validated[Config]) is better than AnalyzeConfig(cfg *Config) with an internal ValidateConfig call.
